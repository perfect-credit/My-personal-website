# Building HIPAA-Compliant Data Warehouses: Star Schemas for Healthcare Analytics

**Published on:** Dev.to, Medium  
**Read time:** 10 minutes  
**Level:** Intermediate

---

## The Challenge

We needed to build a data warehouse for healthcare analytics. Standard warehousing practices—normalized schemas, fast queries, open access for analysts—don't work in healthcare.

Why? **Protected Health Information (PHI).**

Under HIPAA (Health Insurance Portability and Accountability Act), storing patient medical records requires:
- Encryption at rest and in transit
- Access controls (who can see what data)
- Audit trails (who accessed what, when)
- Data lineage (where did this data come from)
- Right to deletion (patient requests must be honored)
- De-identification for secondary use

A traditional Redshift cluster with public schemas and analyst access = a HIPAA violation.

This article covers how we built a warehouse that's fast, analytical, *and* compliant.

---

## The Architecture

```
Patient data (EMR) → Data pipeline (Airflow) → HIPAA warehouse (Redshift) → Analytics & ML
                                                ↓
                                            Audit logs
                                            De-identified copies
                                            Access controls
```

### Core Principles

1. **Never store raw PHI in the warehouse.** Process it before loading.
2. **Encrypt everything.** Data at rest, in transit, in backups.
3. **Access controls by role.** Cardiologists see cardiac patients. Pharmacists see drugs.
4. **Audit trail on every query.** If a patient requests "who accessed my data," you can answer exactly.
5. **Separate identified from de-identified.** Use de-identified copies for ML training.

## The Star Schema Design

We built a star schema with careful PHI handling:

### Dimension Tables (Non-PHI Context)

```sql
-- dim_patient (minimal PHI)
CREATE TABLE dim_patient (
    patient_sk INT PRIMARY KEY,
    patient_id_encrypted VARCHAR(256),  -- Encrypted PII
    date_of_birth DATE,  -- Needed for clinical decisions
    age_group VARCHAR(20),  -- Generalized for privacy
    gender VARCHAR(10),
    zip_code_prefix VARCHAR(5),  -- First 3 digits only (HIPAA safe harbor)
    is_deceased BOOLEAN,
    deceased_date DATE,
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);

-- dim_encounter (visit context)
CREATE TABLE dim_encounter (
    encounter_sk INT PRIMARY KEY,
    patient_sk INT,
    encounter_id_encrypted VARCHAR(256),
    encounter_date DATE,
    encounter_type VARCHAR(50),  -- Inpatient, outpatient, ED
    department VARCHAR(100),
    provider_id_encrypted VARCHAR(256),  -- Encrypted physician ID
    encounter_duration_minutes INT,
    created_at TIMESTAMP
);

-- dim_diagnosis (medical codes)
CREATE TABLE dim_diagnosis (
    diagnosis_sk INT PRIMARY KEY,
    icd10_code VARCHAR(10),
    icd10_description VARCHAR(500),
    is_primary BOOLEAN,
    snomed_code VARCHAR(20),
    created_at TIMESTAMP
);

-- dim_medication (drug codes)
CREATE TABLE dim_medication (
    medication_sk INT PRIMARY KEY,
    drug_code VARCHAR(50),
    drug_name VARCHAR(500),
    therapeutic_class VARCHAR(100),
    generic_name VARCHAR(500),
    created_at TIMESTAMP
);
```

### Fact Table (De-Identified)

```sql
-- fact_clinical_events (de-identified)
CREATE TABLE fact_clinical_events (
    event_sk BIGINT PRIMARY KEY,
    patient_sk INT,  -- Foreign key, encrypted patient ID
    encounter_sk INT,
    diagnosis_sk INT,
    medication_sk INT,
    event_date DATE,
    event_timestamp TIMESTAMP,
    event_type VARCHAR(50),  -- Diagnosis, medication, lab, vital
    event_value DECIMAL(10, 2),  -- e.g., BP, lab result
    event_unit VARCHAR(20),
    severity VARCHAR(20),  -- Mild, moderate, severe
    created_at TIMESTAMP,
    data_source VARCHAR(50),  -- Which EMR system
    source_system_id VARCHAR(256),  -- Encrypted reference to source
    created_by_user_id_encrypted VARCHAR(256),  -- Who entered this
    
    FOREIGN KEY (patient_sk) REFERENCES dim_patient(patient_sk),
    FOREIGN KEY (encounter_sk) REFERENCES dim_encounter(encounter_sk),
    FOREIGN KEY (diagnosis_sk) REFERENCES dim_diagnosis(diagnosis_sk),
    FOREIGN KEY (medication_sk) REFERENCES dim_medication(medication_sk)
);
```

### Key Design Decisions

#### 1. Surrogate Keys Instead of Direct Patient IDs

```sql
-- WRONG: Direct PII in fact table
SELECT patient_name, date_of_birth, diagnosis
FROM facts
WHERE diagnosis LIKE '%Diabetes%';
-- ❌ Any analyst can see patient names

-- RIGHT: Surrogate keys + access controls
SELECT COUNT(*) as patient_count
FROM fact_clinical_events f
JOIN dim_patient p ON f.patient_sk = p.patient_sk
WHERE diagnosis_sk IN (SELECT diagnosis_sk FROM dim_diagnosis WHERE icd10_code LIKE 'E11%')
AND user_has_access('diabetes_research', current_user);
-- ✅ Access controlled
```

#### 2. Encryption of Direct Identifiers

```sql
-- Patient ID, provider ID, encounter ID: all encrypted
ALTER TABLE dim_patient ADD COLUMN patient_id_encrypted VARCHAR(256);

-- Encrypt during load (using AWS KMS or similar)
UPDATE dim_patient SET patient_id_encrypted = 
  aws_kms_encrypt('arn:aws:kms:us-east-1:123456789:key/12345678', patient_id);

-- Only the application layer has decryption keys
-- Analysts never see raw patient IDs
```

#### 3. Generalization for De-Identification

```sql
-- HIPAA Safe Harbor: remove specific identifiers
-- Instead of exact date of birth, use age buckets
ALTER TABLE dim_patient DROP COLUMN date_of_birth;
ALTER TABLE dim_patient ADD COLUMN age_bucket VARCHAR(20);

-- Instead of zip code, use region
ALTER TABLE dim_patient DROP COLUMN zip_code;
ALTER TABLE dim_patient ADD COLUMN region VARCHAR(20);

-- Update
UPDATE dim_patient SET age_bucket = 
  CASE 
    WHEN age < 18 THEN '0-17'
    WHEN age < 30 THEN '18-29'
    WHEN age < 50 THEN '30-49'
    WHEN age < 70 THEN '50-69'
    ELSE '70+'
  END;
```

## Access Controls

Different roles see different data:

```sql
-- Create roles
CREATE ROLE cardiologist_researcher;
CREATE ROLE pharmacist_analyst;
CREATE ROLE data_scientist;

-- Grant permissions by role
GRANT SELECT ON dim_patient TO cardiologist_researcher;
GRANT SELECT ON dim_diagnosis TO cardiologist_researcher;
GRANT SELECT ON dim_medication TO cardiologist_researcher;

-- Add row-level security (Redshift supports this in newer versions)
CREATE POLICY cardiac_data_only ON fact_clinical_events
  USING (
    diagnosis_sk IN (
      SELECT diagnosis_sk FROM dim_diagnosis 
      WHERE therapeutic_class IN ('Cardiac', 'Hypertension')
    )
  );

ATTACH POLICY cardiac_data_only TO cardiologist_researcher;

-- Now this query works:
SELECT COUNT(*) as cardiac_patients
FROM fact_clinical_events
WHERE diagnosis IN ('hypertension', 'MI');

-- But this would fail (blocked by policy):
SELECT COUNT(*) as psych_patients
FROM fact_clinical_events
WHERE diagnosis IN ('depression', 'anxiety');
```

## Audit Logging

Every query is logged. Every data access is traceable.

```sql
-- Audit table
CREATE TABLE audit_log (
    audit_id BIGINT PRIMARY KEY,
    user_id_encrypted VARCHAR(256),
    query TEXT,
    query_hash VARCHAR(64),
    table_accessed VARCHAR(200),
    patient_sk_accessed INT,
    result_row_count INT,
    query_timestamp TIMESTAMP,
    query_duration_seconds INT,
    ip_address VARCHAR(50),
    access_granted BOOLEAN,
    denial_reason VARCHAR(500),
    created_at TIMESTAMP
);

-- Trigger on sensitive tables
CREATE TRIGGER audit_fact_access
AFTER SELECT ON fact_clinical_events
FOR EACH ROW
EXECUTE FUNCTION log_audit('fact_clinical_events', current_user, current_timestamp);

-- Function to log access
CREATE OR REPLACE FUNCTION log_audit(
  table_name VARCHAR, user_id VARCHAR, access_time TIMESTAMP
)
RETURNS VOID AS $$
BEGIN
  INSERT INTO audit_log (user_id_encrypted, table_accessed, query_timestamp, access_granted)
  VALUES (aws_kms_encrypt(user_id), table_name, access_time, TRUE);
END;
$$ LANGUAGE plpgsql;
```

### Audit Query Example

```sql
-- Patient right to access: "Who accessed my data?"
SELECT 
  user_id_encrypted, 
  table_accessed, 
  query_timestamp,
  query_duration_seconds
FROM audit_log
WHERE patient_sk_accessed = (
  SELECT patient_sk FROM dim_patient 
  WHERE patient_id_encrypted = aws_kms_encrypt('patient_123')
)
ORDER BY query_timestamp DESC;

-- Returns:
-- Dr. Smith accessed fact_clinical_events on 2024-01-15 at 10:30 AM (2 seconds)
-- Analytics team accessed dim_diagnosis on 2024-01-14 at 9:15 AM (5 seconds)
-- ...
```

## Data Pipeline (dbt + Airflow)

We use dbt for transformations with built-in testing:

```yaml
# dbt models
models:
  - name: dim_patient
    description: Patient dimension with generalized PII
    columns:
      - name: patient_sk
        description: Surrogate key
        tests:
          - unique
          - not_null
      - name: patient_id_encrypted
        description: Encrypted patient ID
        tests:
          - not_null
      - name: age_bucket
        description: Generalized age (HIPAA Safe Harbor)
        tests:
          - accepted_values:
              values: ['0-17', '18-29', '30-49', '50-69', '70+']

  - name: fact_clinical_events
    description: De-identified clinical events
    freshness:
      warn_after: {hours: 24}
      error_after: {hours: 48}
    columns:
      - name: event_sk
        tests:
          - unique
          - not_null
      - name: patient_sk
        tests:
          - not_null
          - relationships:
              to: ref('dim_patient')
              field: patient_sk
```

### Airflow DAG for Privacy-Aware Loading

```python
from airflow import DAG
from airflow.operators.python import PythonOperator
import boto3
from datetime import datetime

default_args = {
    'owner': 'data-team',
    'start_date': datetime(2024, 1, 1),
    'retries': 3,
}

dag = DAG('hipaa_warehouse_load', default_args=default_args)

def encrypt_pii(**context):
    """Encrypt PII before loading to warehouse."""
    kms = boto3.client('kms')
    
    patient_data = load_from_ehr()
    
    for row in patient_data:
        # Encrypt patient ID
        row['patient_id'] = kms.encrypt(
            KeyId='arn:aws:kms:us-east-1:123456789:key/12345678',
            Plaintext=row['patient_id']
        )['CiphertextBlob']
        
        # Generalize date of birth
        row['age_bucket'] = generalize_age(row['date_of_birth'])
        row['date_of_birth'] = None  # Remove raw DOB
    
    return patient_data

def load_to_warehouse(**context):
    """Load encrypted data to Redshift."""
    data = context['task_instance'].xcom_pull(task_ids='encrypt_pii')
    
    # Load via S3 (encrypted)
    s3 = boto3.client('s3')
    s3.put_object(
        Bucket='hipaa-warehouse-staging',
        Key=f'encrypted-data-{datetime.now().isoformat()}.parquet',
        Body=data,
        ServerSideEncryption='aws:kms'
    )
    
    # Redshift COPY command with encryption
    redshift = boto3.client('redshift-data')
    redshift.execute_statement(
        ClusterIdentifier='hipaa-warehouse',
        Database='healthcare_dw',
        Sql="""
        COPY dim_patient FROM 's3://hipaa-warehouse-staging/encrypted-data-*.parquet'
        ENCRYPTED
        CREDENTIALS 'aws_iam_role=arn:aws:iam::123456789:role/redshift-role'
        FORMAT PARQUET;
        """
    )

def run_dbt_tests(**context):
    """Validate data quality after load."""
    import subprocess
    subprocess.run(['dbt', 'test', '--models', 'dim_*,fact_*'], check=True)

encrypt_task = PythonOperator(
    task_id='encrypt_pii',
    python_callable=encrypt_pii,
    dag=dag,
)

load_task = PythonOperator(
    task_id='load_to_warehouse',
    python_callable=load_to_warehouse,
    dag=dag,
)

test_task = PythonOperator(
    task_id='run_dbt_tests',
    python_callable=run_dbt_tests,
    dag=dag,
)

encrypt_task >> load_task >> test_task
```

## De-Identification for ML

For machine learning, we create a separate de-identified copy:

```sql
-- Create de-identified view
CREATE VIEW fact_clinical_events_deidentified AS
SELECT 
    patient_sk,  -- Keep surrogate key for analysis
    encounter_date,  -- Keep date for temporal analysis
    diagnosis_sk,
    medication_sk,
    event_type,
    event_value,
    severity,
    -- Remove or generalize identifiers
    NULL AS created_by_user_id_encrypted,  -- Remove who entered data
    NULL AS provider_id_encrypted,  -- Remove physician identity
    NULL AS source_system_id  -- Remove EMR system reference
FROM fact_clinical_events;

-- Use for ML training (HIPAA Safe Harbor)
SELECT * FROM fact_clinical_events_deidentified 
WHERE event_date BETWEEN '2023-01-01' AND '2023-12-31';
```

## Compliance Checklist

Before going live, we validate:

```sql
-- 1. All PII encrypted?
SELECT COUNT(*) FROM dim_patient WHERE patient_id IS NOT NULL;
-- Should be 0 (all encrypted)

-- 2. No data exposed in logs?
SELECT query FROM audit_log 
WHERE query LIKE '%patient_name%' OR query LIKE '%SSN%';
-- Should be empty

-- 3. Access controls in place?
SELECT * FROM information_schema.role_privilege_grants 
WHERE grantee = 'cardiologist_researcher';
-- Should show restricted access

-- 4. Audit trail functional?
SELECT COUNT(*) FROM audit_log WHERE query_timestamp > NOW() - INTERVAL 24 HOUR;
-- Should show all recent queries logged

-- 5. De-identification working?
SELECT COUNT(*) FROM fact_clinical_events_deidentified 
WHERE created_by_user_id_encrypted IS NOT NULL;
-- Should be 0
```

## Key Takeaways

1. **HIPAA compliance isn't add-on. It's architectural.** Design for encryption, access control, and auditing from day one.

2. **Use surrogate keys, not patient IDs.** Analysts never see raw PHI. Reduces risk exponentially.

3. **Encrypt direct identifiers at load time.** Before data hits the warehouse, encrypt it. Make it irreversible.

4. **Audit everything.** Every query is logged. Every access is traceable. This is the most powerful compliance tool.

5. **De-identify for secondary use.** Keep an identified warehouse for clinical operations. Create a de-identified copy for ML/research. Clear separation.

6. **Test compliance, not just functionality.** Your dbt tests should include "no PII in this column" checks.

## Closing

Healthcare data warehouses are held to a different standard than typical analytics systems. There's no "move fast and break things" in medicine.

But HIPAA-compliant doesn't mean slow or inflexible. With thoughtful schema design, access controls, and audit logging, you get a system that's compliant, performant, and auditable.

The upfront complexity pays off in confidence: you know exactly who accessed what, when. You can answer patient questions instantly. You can prove compliance to regulators.

That's worth the engineering effort.
